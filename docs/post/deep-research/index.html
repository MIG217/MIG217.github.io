Langchain Open Deep Research Agent 具有高度可配置性，支持添加自定义 MCP 服务器，并且是开源的，因此可以根据自己的具体需求进行定制。

Open Deep Research Architecture#

Langchain Deep Research Agent 的运行可分为 三个阶段：

  1. Scoping the Problem

代理可以向用户提出澄清性问题，然后将整个对话历史压缩为一份Research Brief

  1. Research Phase

在研究阶段，系统会有一个 主管代理（Supervisor） 来统筹全局，它会派出多个 子代理（Sub Agents），每个子代理专注于不同的子问题。

  • 子代理完成研究后，将结果返回给主管代理。
  • 主管代理会综合分析这些结果，决定是否需要进一步研究，或结束研究。
  1. Report Writing

当研究完成后，代理会将所有结果整合，并通过一次性调用写作 LLM，生成一份 最终报告。这份报告会直接返回给用户.

Phase 1: Scope#

在 范围界定阶段，我们的目标是让代理真正理解用户的需求，这个过程主要分为 两步：

  1. 与用户进行澄清性问答
  2. 生成研究简报（Research Brief）

User Clarification#

用户往往在最初的请求中遗漏重要信息。因此，代理的第一步是主动提问，以获取足够的上下文。我们还允许代理根据需要提出后续问题，直到它认为已经收集到所有关键信息。

如果开始给出的提问过于模糊，代理便自动生成了一个澄清性问题。在我提供了详细信息后，代理会确认上下文是否完整，判断是否需再追问。

Brief Generation#

核心目标： 将沟通内容压缩成一个清晰、可执行的任务目标。

当澄清性对话结束后，我们可能会得到一个包含多轮问答的聊天记录。为了避免 Agent 在冗长的对话中迷失方向，我们会执行一个关键操作：将至今为止的所有对话（包括最初的请求和后续的补充信息）合成为一份研究简报 (Research Brief)。

这份简报会被保存到代理的状态中，并在后续的 研究阶段和写作阶段多次引用,确保每一步行动都与最初确定的目标保持一致。

Phase 2: Research#

研究阶段是一个高度开放的过程，因为深度研究代理所面对的问题类型千差万别，需要足够的灵活性来应对。为了适应这种多样性，我们在初始研究阶段采用了 极简的框架设计。

Supervisor and Sub-agent#

Supervisor

Supervisor分析研究简报，判断问题是否可以并行拆解。如果问题可以分解成多个独立子问题，主管代理就会启动多个Sub Agents 进行并行研究；如果问题本身无法拆分，它也可以选择单线程研究。

这种方式本质上是一种 上下文工程（Context Engineering） 策略：与其让代理直接处理一个庞杂的问题，不如把它分割成可管理的小块，每个子代理只需聚焦于一个具体子主题。

Sub-agent

每个Sub-agent 可以在自己独立的上下文窗口中，专注于研究一个孤立的子主题。

子代理本质上都是一个工具调用循环 (Tool-calling loop)。这种设计的最大优势之一是其高度的可配置性。Agent 可以使用我们默认提供的 Tavily 搜索工具，也可以调用我们提供给它的任何自定义工具。

循环会持续进行，直到 Agent 调用一个名为 research_complete 的特殊工具。这个工具本身不执行任何操作，它仅仅是一个信号，告诉我们 LLM 对其研究结果感到满意。

结果清理与压缩#

在子代理将研究结果返回给监督者之前，还有一个至关重要的压缩步骤。

问题所在： 工具的输出通常非常混乱。例如，航班搜索结果可能是一个巨大的 JSON 文件，其中夹杂着大量无关信息和零散的 token。如果将这些原始数据直接塞给监督者，会导致两个问题：

  • Token 膨胀: 快速逼近上下文窗口的上限。
  • 信息噪音: 大量杂乱、无关的信息会干扰监督者的判断。

解决方案： 子代理在返回前会执行一个“清洗步骤”，为监督者生成一份清晰、全面的“迷你报告”。

我们在System Prompt特意强调要保留所有相关信息和来源，并将其描述为一个“清洗”步骤，而不是“总结”，以防止 Agent 意外地丢弃有价值的信息。

这份清洗后的报告通常包含：

  • 执行过的所有搜索和工具调用记录。
  • 一份全面、详尽的发现清单。
  • 一个完整的参考来源列表。

研究迭代#

当主管代理收到所有子代理返回的“压缩报告”后，它会基于这些上下文做出决定：

  • 如果信息已经足够，它会结束研究。
  • 如果发现还有信息缺口，它会继续启动新的子研究，直到对结果满意为止。

这种迭代过程高度类似于我们人类做研究时的思维方式：对于简单问题，初步搜索即可得到满意答案；但对于复杂问题，则需要逐步深入探索。

Phase 3: Report Writing#

在最终撰写研究报告时，并行写作并不理想。最初尝试将报告拆分成多个部分并行生成，结果常常导致报告内容割裂、不连贯。经过多次试验，最终确认：将所有压缩后的研究成果集中起来，一次性生成完整报告（oneshot）是最有效的方式。

这个阶段的关键在于：我们在前面各子代理返回结果时，进行了压缩处理。这一步极大降低了上下文窗口的压力，让最终报告生成代理能够高效、连贯地组织信息。如果跳过压缩步骤，让最终代理直接处理各子代理原始输出，往往会因为上下文过于庞杂、冗余内容太多而“崩溃”，生成的报告质量也大打折扣。

通过这种方式，主代理只接收到一份干净、结构清晰的研究总结列表，从而能一次性完成整份报告的撰写。

至此，便是Open Deep Research全流程架构。
