在当下的 AI 应用开发中，模型本身的智能水平固然重要，但如果无法高效接入外部数据和工具，模型的价值就会大打折扣。很多开发者不得不为不同的数据源、API 或工具重复实现集成逻辑，这不仅增加了开发成本，也让应用难以复用和扩展。

为了解决这一问题，Anthropic 团队与开源社区共同推动了 Model Context Protocol（MCP）。**MCP 是一种开放协议，旨在标准化 LLM 应用与外部系统的连接方式，让模型可以像调用 REST API 一样，统一地访问各类工具与数据源。**

## MCP Architecture

MCP 遵循经典的客户端-服务器 (Client-Server) 架构模式。在这个模式中，主要有三个核心角色：

1. **Host**: 指希望通过 MCP 访问数据的大模型应用，例如 Claude Desktop、IDE、AI Agent 等。
2. **MCP Servers**: 是一些 轻量级程序，通过 MCP 协议对外暴露特定功能（capabilities），比如访问数据库、调用搜索服务或执行 API。
3. **MCP Clients**: 在宿主应用内部，与 MCP Server 保持 1:1 连接，用于管理通信。

### MCP 核心要素

在进一步讨论客户端和服务器的职责之前，我们需要先了解 MCP 协议中几个最核心的组成部分：工具（Tools）、资源（Resources） 和 提示模板（Prompt Templates）。

![](/static/images/how-does-it-work.png)

**Tools**

如果您熟悉大模型领域的“工具使用 (Tool Use)”，那么 MCP 中的工具概念会非常亲切。

- 定义：工具本质上是可由客户端调用的函数，通常用于执行修改性或写入型的操作。
- 功能：检索数据、执行搜索、发送消息、更新数据库记录等。
- 类比：可以将其理解为 `POST` 或 `UPDATE` 请求，代表着一个需要服务器去执行的“动作”。

**Resources**

与工具不同，资源是服务器提供的只读数据或上下文。

- 定义：由服务器暴露的只读数据。客户端可以选择是否使用这些资源，但不会对其进行修改。
- 功能：提供上下文信息，例如数据库记录、API 响应、文件内容、PDF 文档等。
- 类比：类似于一个 `GET` 请求，目的是获取“信息”而非执行操作。

**Prompt Template**

这是 MCP 一个非常巧妙的设计，旨在减轻用户的提示词工程 (Prompt Engineering) 负担。

- 定义：预先定义好的、存储在服务器上的高质量提示词模板。
- 解决的问题：假设一个 MCP 服务器的功能是“查询 Google Drive 并总结内容”，如果没有模板，用户需要自己摸索如何写出最高效的指令。而提示词模板则提供了“最佳实践”，让用户可以一键使用，轻松获得理想结果。
- 价值：将复杂的指令封装成简单易用的模板，客户端可以直接获取并呈现给用户，极大地提升了用户体验。

**职责分工总结**

基于这三大要素，客户端和服务器的角色变得非常清晰：

- 服务器 (Server) 的职责：暴露 (Expose) 自己的能力，即向外提供可用的工具、资源和提示词模板。

- 客户端 (Client) 的职责：
  - 发现 (Find) 服务器提供了哪些可用的工具和资源。
  - 根据需要调用 (Invoke) 这些能力。

### MCP 的通信机制

了解了核心要素后，我们再来看看客户端和服务器之间是如何进行通信的。

**1. 通信的生命周期**

MCP 的连接过程遵循一个清晰的生命周期，分为三个阶段：

1. 初始化 (Initialization)：客户端与服务器建立连接，通过“请求-响应-通知”的握手流程，确认双方准备就绪。

2. 消息交换 (Message Exchange)：连接建立后，双方可以进行双向通信。不仅客户端可以向服务器发请求（调用工具、获取资源），服务器也可以主动向客户端发送请求或通知。

3. 终止 (Termination)：通信结束，连接被关闭。

核心特点：MCP 的通信是双向的，这使得它比传统的“一问一答”模式更加灵活和强大。

2. **消息的载体：传输协议 (Transports)**

Transport 决定了底层消息的传输方式，根据部署环境的不同而变化：

- **本地服务器**：使用标准输入输出 (Stdio)。客户端将服务器作为子进程启动，通过管道进行高效的本地通信。

- **远程服务器**：

  - HTTP + SSE (旧)：一种有状态 (Stateful) 的长连接方式，服务器可以主动向客户端推送事件。

  - Streamable HTTP (推荐)：新一代协议，同时支持有状态和无状态 (Stateless) 连接。它既能兼容 SSE 的长连接模式，也支持常规的 HTTP 请求-响应模式，更适合现代云原生和可扩展的应用部署。

## Creating an MCP Server

在创建一个 MCP Server 时，假设它需要对外暴露一些工具（tools）。那么，这个服务器至少要处理来自客户端的两类主要请求：

1. ListToolsRequest

- 作用：客户端用它来请求服务器“有哪些工具可用”。
- 服务器需要返回一个工具清单（tools list），告诉客户端当前能调用的工具有哪些。

2. CallToolRequest

- 作用：客户端用它来请求调用某一个具体的工具。
- 服务器需要接收这个请求，解析参数，执行对应工具的逻辑，并返回执行结果。

### 实现方式

- **底层实现 (low-level implementation)：**

在这种方式下，你需要自己直接处理不同类型的请求（比如 ListToolsRequest 和 CallToolRequest）。也就是说，整个通信协议的细节都要你来实现和控制。好处是灵活性最高，你可以完全定制服务器的行为和逻辑，但代价是开发复杂度高、代码量大。


- **高层实现（使用 FastMCP）：**
FastMCP 提供了一个更高层的接口，让你更快、更简单地构建 MCP 服务器。在这种方式下，你只需要把工具定义成函数，至于底层协议的处理、请求的解析和响应的构造，都由 FastMCP 自动完成。这样大大减少了你需要关注的底层细节，适合快速开发和迭代。
